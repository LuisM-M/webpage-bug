Bug hunt guide: what to check, in order

Work top to bottom. Fix one, run npx jest, then move on. Data bugs come first because wrong data gets cached and makes later bugs look different than they are.

Red block = wrong codeGreen block = correct codeYellow = what to look forBold highlight inside a block = the exact part that matters

0Before touching code

Run npx jest. Read each failing test's name and the Expected vs Received lines. That is your spec. Then open the route file for the failing endpoint and follow it: route, then service or repository, then back.

  • File named app_test.js? Jest only finds *.test.js, *.spec.js or __tests__/. Rename it.
  • app.js must end with module.exports = app and must not call listen. Only server.js does.

1Repository: filters and total

Look in: repository.js / the data layer. Symptoms: filter tests return everything; total is 4 when you expect 2.

let results = [...this.events];
// no filters
const offset = (page - 1) * limit;
return { events: results.slice(offset, offset + limit),
         total: this.events.length };   // counted before filtering
let results = [...this.events];                       // copy, never mutate
if (status)   results = results.filter(e => e.status === status);
if (category) results = results.filter(e => e.category === category);
const total = results.length;                        // AFTER filter, BEFORE slice
const offset = (page - 1) * limit;
return { events: results.slice(offset, offset + limit), total };

Common mistakes

  • Order wrong: filter, then count, then slice. Never count after slicing.
  • Filter runs even when the param is missing (filter(e => e.status === undefined) returns nothing). Wrap in if (param).
  • Using = instead of ===, or comparing different letter case.
  • .sort(), .splice() or .reverse() on this.events changes the original data.

2Route: page and limit normalization

Look in: the top of the GET handler. Symptoms: limit=0 gives 11 instead of 1; limit=250 not capped; negative page not fixed. Remember req.query values are strings.

const page  = Math.max(1, parseInt(req.query.page) || 1);
const limit = Math.min(100, Math.max(1, parseInt(req.query.limit) || 11));
// 0 is falsy, so limit=0 falls back to the default. 11 also does not match the repo default of 10.
const toInt = (v, fallback) => {
  const n = parseInt(v, 10);
  return Number.isNaN(n) ? fallback : n;
};
const page  = Math.max(1, toInt(req.query.page, 1));
const limit = Math.min(100, Math.max(1, toInt(req.query.limit, 10)));

Common mistakes

  • Forgetting Math.max(1, ...) on page, or Math.min(100, ...) on limit.
  • Only clamping the max, so limit=0 or -5 still breaks.
  • Defaults that disagree between route (11) and repository (10).
  • Passing raw req.query.page (a string) to the repository instead of the clamped number.

3Response: pagination fields

Look in: where the response object is built. Test expects six fields with exact names.

pagination: {
  page: page || 1,
  limit: limit || 10,
  total
}   // totalPages, hasNextPage, hasPreviousPage missing
const totalPages = Math.ceil(total / limit);
pagination: {
  page, limit, total,
  totalPages,
  hasNextPage: page < totalPages,
  hasPreviousPage: page > 1
}

Common mistakes

  • Math.floor instead of Math.ceil (4 items, limit 3 must give 2 pages).
  • hasNextPage: page <= totalPages (off by one; should be <).
  • hasPreviousPage: page >= 1 (should be > 1).
  • Field names misspelled (hasNextpage). Copy them from the test.

4Cache key

Look in: the line that builds cacheKey. Symptom: two equivalent requests (page=0&limit=250 and page=1&limit=100) make two cache entries, but the test expects size 1.

const cacheKey = `events:${req.query.status}:${req.query.category}:${req.query.page}:${req.query.limit}`;
// raw strings, and "undefined" ends up inside the key
const cacheKey = `events:${status || 'all'}:${category || 'all'}:${page}:${limit}`;
// built from the NORMALIZED page and limit variables

Common mistakes

  • Building the key before normalizing, so it captures raw input.
  • Leaving a param out of the key (wrong data served for other filters).
  • Dropping the events: prefix, which makes step 6 impossible.

5CacheService: prefix deletion

Look in: the cache class (Map or Redis wrapper). The code has a hint comment asking for a method that deletes keys starting with a prefix.

clear() { this.store.clear(); }
// no deleteByPrefix
clear() { this.store.clear(); }
deleteByPrefix(prefix) {
  for (const key of this.store.keys()) {
    if (key.startsWith(prefix)) this.store.delete(key);
  }
}

Common mistakes

  • Calling this.store.startsWith (a Map has no such method; check each key).
  • Deleting only one exact key. A listing has many variants, so use the prefix.
  • Writing it, then never calling it (step 6).

6Invalidate the cache on writes

Look in: app.post and app.patch (and delete if present). Symptom: after a POST or PATCH, the GET still returns old data.

app.post('/api/events', (req, res) => {
  const newEvent = repo.createEvent(req.body);
  // TODO: invalidate cached lists
  res.status(201).json(newEvent);
});
app.post('/api/events', (req, res) => {
  const newEvent = repo.createEvent(req.body);
  app.locals.cache.deleteByPrefix('events:');   // after the change, before responding
  res.status(201).json(newEvent);
});

Common mistakes

  • Invalidating before the data changes, so a request can re-cache the old data.
  • Fixing POST but forgetting PATCH (or DELETE).
  • Prefix typo: 'event:' vs 'events:' silently deletes nothing.
  • Calling this.cache or cache when the variable is app.locals.cache.

7Status codes and missing-data handling

Look in: PATCH and any route that takes an :id. Symptom: a test expects 404 or 400 and gets 200. Usually a secondary fix, so do it after steps 1-6.

app.patch('/api/events/:id/status', (req, res) => {
  repo.updateStatus(req.params.id, req.body.status);
  res.status(200).send();    // 200 even when the id does not exist
});
app.patch('/api/events/:id/status', (req, res) => {
  const updated = repo.updateStatus(req.params.id, req.body.status);
  if (!updated) return res.status(404).json({ error: 'Event not found' });
  app.locals.cache.deleteByPrefix('events:');
  res.status(200).json(updated);
});

Common mistakes

  • Missing return before the early res, which causes "Cannot set headers after they are sent".
  • Creating with 200 instead of 201.
  • Invalidating the cache even though nothing changed (404 path).

8Only if the repo uses Redis: async traps

Look in: every cache.get / set / del call. Symptom: responses of {}, the cache always "hits", or Promise { <pending> } in logs.

app.get('/api/events', (req, res) => {
  const cached = redis.get(key);          // a Promise, always truthy
  if (cached) return res.json(cached);
  ...
  redis.set(key, body);                    // object, must be a string
});
app.get('/api/events', async (req, res, next) => {
  try {
    const cached = await redis.get(key);
    if (cached) return res.json(JSON.parse(cached));
    ...
    await redis.set(key, JSON.stringify(body), { EX: 60 });
    res.json(body);
  } catch (err) { next(err); }
});

Common mistakes

  • One missing await anywhere in the chain (also on deleteByPrefix in POST and PATCH).
  • Skipping JSON.stringify on write or JSON.parse on read.
  • Never calling await client.connect() at startup.
  • Using KEYS * for prefix deletion. Use scanIterator with MATCH: 'events:*'.
  • Using await inside forEach. Use for...of instead.

9Final pass

  • Remove the debug console.log lines.
  • Run the whole suite once more: npx jest.
  • Reproduce one case by hand: curl "localhost:3000/api/events?page=-5&limit=250" should return page 1, limit 100.
